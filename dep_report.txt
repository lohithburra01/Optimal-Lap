How they interact
The Track Visualizer script's earlier failed installs left a stale copy of numpy 2.4.x inside Blender's user scripts\modules\ directory — the same shared folder that Blender automatically puts on sys.path for every addon. When launch_control_auto_car_rig later did import numpy, Python's resolver picked up that stale 2.4.x copy instead of Blender's bundled 1.26.4, which crashed the addon at startup with ImportError: cannot load module more than once per process.

So both issues had the same root: the Track Visualizer was installing third-party Python packages into a shared location. Fixing the Track Visualizer's install logic prevents this pollution from happening again. Existing affected machines also need a one-time cleanup of the shared modules\ directory (Section 2).

1.1 — quadprog cannot be installed because pip falls back to a source build
Original error from the install log:

quadprog/quadprog.cpp(44): fatal error C1083:
    Cannot open include file: 'Python.h': No such file or directory
ERROR: Failed building wheel for quadprog
Failed to install trajectory-planning-helpers ... non-zero exit status 1.
Root cause (two layers)
Blender's bundled Python ships without development headers. …\Blender 4.5\4.5\python\ contains only bin\, DLLs\, lib\. There is no include\Python.h, so any C extension that has to be built from source cannot compile against Blender's Python.

pip install trajectory-planning-helpers resolves quadprog as a transitive dependency. The quadprog version pip resolved had no prebuilt cp311 win_amd64 wheel on PyPI, so pip silently fell back to a source build that then failed for reason (1).

The dict in check_dependencies() listed trajectory_planning_helpers before quadprog. Pip therefore installed trajectory-planning-helpers first and pulled in latest unpinned quadprog as a transitive dep — the explicit quadprog entry never got the chance to use a pinned version.
Fix
Three coordinated sub-changes:

Pin quadprog to a version with a published cp311 win_amd64 wheel: quadprog>=0.1.12. (0.1.11 is cp36–cp310 only.)
Move quadprog to come before trajectory_planning_helpers in the dict so the pin takes effect at resolution time.
Pass --only-binary=:all: --prefer-binary to pip so it refuses to attempt source builds. If a wheel is missing, pip now fails fast with a clear "Could not find a version that satisfies …" instead of producing 200 lines of MSVC errors.

1.2 — PermissionError [WinError 5] on numpy\fft\_pocketfft_umath.cp311-win_amd64.pyd
Error from install log:

PermissionError: [WinError 5] Access is denied:
  '…\modules\numpy\fft\_pocketfft_umath.cp311-win_amd64.pyd'
…in pip _handle_target_dir → shutil.rmtree(target_item_dir)
Root cause
After pip writes wheels to a staging directory, pip._internal.commands.install._handle_target_dir does, for each item in staging:

if os.path.exists(target_item_dir):
    if upgrade:
        shutil.rmtree(target_item_dir)   # ← fails here on Windows
    else:
        # log "already exists, specify --upgrade to force replacement"
        continue
shutil.move(staging_item, target_item_dir)

That shutil.rmtree on the existing package directory in --target calls os.unlink on every file inside. On Windows, any .pyd (a Windows DLL) memory-mapped into a running process is locked. Blender itself loads the bundled site-packages numpy at startup — _pocketfft_umath.pyd is mapped into the Blender process — so when pip tries to delete the same-named file in modules\numpy\fft\ (it's a different path but Windows still holds the handle for the previously imported one), the unlink fails with WinError 5.
Fix (incomplete — superseded in Section 1.3)
The first attempt was to drop --upgrade. Without --upgrade, pip skips items that already exist in the target dir (with a warning) instead of trying to delete-then-replace them. No rmtree, no lock collision.

This created a new bug (Section 1.3): without --upgrade, pip skips the package code directory (pandas/) but still writes the new metadata directory (pandas-3.0.2.dist-info/), producing a Frankenstein install that looks present but cannot be imported. The proper fix in Section 1.3 lets us keep --upgrade safely.


1.3 — Install reports "All installed!" but check_dependencies() still says everything is missing
After the Section 1.2 fix, the install operator reported success but the addon panel still claimed fastf1, pandas, scipy, quadprog, trajectory-planning-helpers were missing — even after restarting Blender.
Diagnosis
A directory listing of …\Blender\4.5\scripts\modules\ revealed multiple *.dist-info directories per package:

fastf1-3.8.1.dist-info   fastf1-3.8.2.dist-info
numpy-2.4.2.dist-info    numpy-2.4.4.dist-info
pandas-2.3.3.dist-info   pandas-3.0.2.dist-info
cryptography-46.0.5.dist-info  …-46.0.7.dist-info  …-47.0.0.dist-info
…

This is the side-effect of dropping --upgrade. Pip's _handle_target_dir works per item:

pandas-3.0.2.dist-info/ is moved cleanly (no existing dir of that exact versioned name).
pandas/ package directory exists from the prior install → without --upgrade, pip skips it.

Result: old pandas/ code paired with new pandas-3.0.2.dist-info/ metadata. The mismatch makes import pandas raise ImportError, which check_dependencies() catches and reports as missing.
Root fix — isolated dependencies directory
Stop installing into the shared user modules\ directory entirely. The addon now installs into its own subdirectory modules\f1_track_visualizer_deps\. That gives us:

A directory we own exclusively. Other addons don't write here. It can be wiped/reinstalled freely.
With --upgrade safely back in play — nothing else in the Blender process has these specific .pyd files mapped at install time, provided the user installs before triggering an addon operator that imports numpy/scipy/etc. (See operational notes at the end of this section.)
No conflict with other addons' transitive deps that already exist in modules\.
No more pollution of the shared modules\ directory — which is what was breaking launch_control_auto_car_rig (see Section 2).

The isolated dir is then prepended to sys.path (via sys.path.insert(0, …)), so it shadows any leftover wheels in the parent modules\.
get_modules_path() — diff
# BEFORE
def get_modules_path():
    return bpy.utils.user_resource("SCRIPTS", path="modules", create=True)

# AFTER
def get_modules_path():
    # Isolated dependencies dir for this addon. Living under modules/ but in
    # our own subfolder lets us install/upgrade/clean without colliding with
    # other addons' deps (or leftover stale wheels from earlier failed runs).
    return bpy.utils.user_resource(
        "SCRIPTS", path="modules/f1_track_visualizer_deps", create=True
    )
append_modules_to_sys_path() — diff
# BEFORE
def append_modules_to_sys_path(modules_path):
    if modules_path not in sys.path:
        sys.path.append(modules_path)
        site.addsitedir(modules_path)

# AFTER
def append_modules_to_sys_path(modules_path):
    # Insert at the FRONT so our isolated wheels shadow any stale copies
    # that earlier install attempts left in <user>/modules/.
    if modules_path in sys.path:
        sys.path.remove(modules_path)
    sys.path.insert(0, modules_path)
    site.addsitedir(modules_path)
install_package_to_blender() — diff (final form combining 1.1 + 1.3)
# BEFORE
def install_package_to_blender(package, modules_path):
    try:
        subprocess.check_call([
            sys.executable, "-m", "pip", "install",
            "--upgrade", "--target", modules_path, package
        ])
        return True
    except subprocess.CalledProcessError as e:
        print(f"Failed to install {package}: {e}")
        return False

# AFTER
def install_package_to_blender(package, modules_path):
    # --upgrade is needed so pip replaces stale package dirs (without it, pip
    # skips any existing dir and we end up with old code + new dist-info).
    # Safe in our isolated deps dir: nothing else mmaps these .pyd files until
    # an operator imports them, so the rmtree-and-replace step won't lock.
    try:
        subprocess.check_call([
            sys.executable, "-m", "pip", "install",
            "--upgrade", "--target", modules_path,
            "--only-binary=:all:", "--prefer-binary",
            package
        ])
        return True
    except subprocess.CalledProcessError as e:
        print(f"Failed to install {package}: {e}")
        return False

1.4 — Latent risk: bundled-numpy ABI mismatch
Heads-up for the developer (not currently affecting the user, but worth knowing).

After the cleanup in Section 2, the addon's isolated dir contains numpy 2.4.4, while Blender's bundled numpy 1.26.4 is the one that gets loaded into the process at startup. Because Blender imports its own numpy before any addon register() runs, numpy is already in sys.modules by the time our addon's sys.path.insert(0, …) takes effect — meaning import numpy returns the bundled 1.26.4 even though our isolated dir has 2.4.4.

For most operations this is fine — modern wheels (pandas 2.x, scipy ≥ 1.13, fastf1, etc.) ship a "NumPy 2.0 ABI compatibility" build that loads against either 1.x or 2.x. But if a user reports an error like numpy.dtype size changed or module compiled against numpy 2.x, downgrade the deps to numpy-1.26-compatible versions:

# Suggested pins if ABI mismatches arise:
required = {
    "fastf1":   "fastf1",
    "pandas":   "pandas<2.3",       # 2.2.x is reliably 1.26-friendly
    "scipy":    "scipy<1.13",       # 1.13 starts requiring numpy 2
    "quadprog": "quadprog>=0.1.12",
    "trajectory_planning_helpers": "trajectory-planning-helpers<0.55",
}

The cleanest correct fix is to never ship our own numpy and rely entirely on the bundled one — that requires installing every dep with --no-deps and explicitly listing every transitive dep. Heavier change; not required yet.

2.2 — Root cause
Two different versions of numpy were findable in the same Python process:

Blender's bundled numpy 1.26.4, located at …\Blender 4.5\4.5\python\Lib\site-packages\numpy\. Loaded by Blender itself at startup.
A stale numpy 2.4.x, located at …\Blender\4.5\scripts\modules\numpy\ — left over from earlier failed installs of the Track Visualizer (Section 1).

Blender's user scripts\modules\ directory outranks bundled site-packages on sys.path, so when this addon ran import numpy, Python's resolver picked the rogue 2.4.x. numpy 2.x's C extension _multiarray_umath then noticed at init time that another _multiarray_umath-shaped extension was already loaded in the process (from bundled 1.26.4, via Blender's startup) and fired its self-protection guard.

This addon did nothing wrong. Its import numpy is a perfectly normal statement that worked on this machine until the Track Visualizer's failed install attempts left a numpy in scripts\modules\.
2.3 — Fix applied (one-time system cleanup, no code change)
Run with Blender closed:

$mods = "C:\Users\bhavi\AppData\Roaming\Blender Foundation\Blender\4.5\scripts\modules"
Get-ChildItem -LiteralPath $mods -Force |
    Where-Object { $_.Name -ne 'f1_track_visualizer_deps' } |
    Remove-Item -Recurse -Force -Confirm:$false

What this does: removes every loose package from user modules\ (numpy, pandas, scipy, fastf1, matplotlib, contourpy, kiwisolver, fonttools, pillow, packaging, pyparsing, charset_normalizer, certifi, attrs, cattrs, cryptography, idna, msgpack, pycparser, pydantic, pydantic_core, pyjwt, pytz, python_dateutil, rapidfuzz, requests, requests_cache, signalrcore, six, timple, trajectory_planning_helpers, tzdata, typing_extensions, typing_inspection, url_normalize, urllib3, websockets, …) and all their *.dist-info siblings, while preserving the Track Visualizer's f1_track_visualizer_deps\ subfolder.

Some .pyd/.dll files were locked on the first attempt because Blender was still running in the background; once Blender was fully closed they deleted on retry.

After cleanup, import numpy falls through to Blender's bundled 1.26.4 (the only copy of numpy left findable in the process) and launch_control_auto_car_rig enables cleanly.
2.4 — What this addon's developer should know
Nothing to integrate. The addon code is fine.

The breakage was caused by another addon (the Track Visualizer) writing third-party packages — including a different major version of numpy — into Blender's shared user scripts\modules\ directory. When that other addon's install fails partway through, the leftover state shadows Blender's own bundled numpy and breaks anyone who imports numpy.

Best defence (optional, not required): wrap the top-level import numpy as np in panels.py and any other entry-point modules with a try/except that surfaces a clearer error message pointing at the user's scripts\modules\ directory. Example:

try:
    import numpy as np
except ImportError as e:
    raise ImportError(
        "numpy failed to load. This is usually caused by a stale numpy "
        "in '<user>/Blender/<version>/scripts/modules/' from another "
        "addon's failed install. Close Blender, delete that numpy folder, "
        "and restart. Original error: " + str(e)
    ) from e

This is purely cosmetic — it doesn't fix anything, just turns a confusing trace into a self-explaining one.
